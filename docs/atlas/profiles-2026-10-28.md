# Window CPU profiles (2026-10-28)

Lua CPU profiles of the measured game day (1 game day after a 1 game hour warm-up), XL scenario at speed 2, with the `steady_hearth` defaults (RT1, RT2, RT6 and, on ACE, X7 fixes on; T1 variants and the plan clip off). Profiler runs are diagnostic and never timing-valid. Shares are of Lua samples (the profiler accumulates time per Lua function; time inside a C function called from Lua is charged to the calling Lua function). Reports: `tools/profile_report.py <run>/profiler_output-Stonehearth.v1.1.0.949/server_<timestamp>`.

The ACE restock director's nearby-item search dominates:

| Function (ACE `services/server/inventory/restock_director.lua` unless noted) | Self | Inclusive |
| :--- | ---: | ---: |
| Filter closure built by `_filter_to_filter_fn` (lines 1143 to 1185, where the profiler files closures under the enclosing function's range, and the per-line counts sit on lines 1147 to 1160) | 18.0% | 18.0% |
| `best_filter_fn` (line 782, created per errand in `_generate_next_errand`) | 10.6% | 23.8% (its `return filter_fn(item)` is a tail call, so the 18.0% above is not included) |
| `_is_higher_priority_for_item` (line 888) | 7.8% | 13.2% |
| `Inventory:container_for` (base `inventory.lua:998`, called from the priority check) | 5.7% | 5.7% |
| `DesiresTracker:get_needed_material_count` (base) | 2.8% | |

Together about 42% of ACE's Lua samples are the per-candidate evaluation of the restock nearby-item filter. The individual calls are already optimized (the closure is marked as a hotspot), and the volume accounts for the difference. Base passes the shared per-filter-key `filter_fn` to `NearbyItemSearch` (`restock_director.lua:541`), while ACE passes `best_filter_fn`, a new closure per errand (`:806`). `NearbyItemSearch:_search` keys a spatial cache by `tostring(filter_fn)`, and `AiService:create_spatial_cache` (base `ai_service.lua:632`) creates a native spatial cache for every new filter function and keeps it for the session (`rawset(SPATIAL_CACHES, filter_fn, true)`, no-op destructor, Radiant's own comment notes switching to the safe variant "to catch cases where filter functions are not shared"). As a result, restock errands with ACE create native spatial caches whose filters continue being evaluated, and the cost can grow over time. Verified with a census counter (finding R7).

### Probes after the window

- Client CPU profile: calling `radiant:toggle_cpu_profile` from the client's Lua state succeeds, but the 60-second profile it produces is a second `server_*` output with server functions (restock director, server AI service) and no client functions. That call controls the server profiler only, so the client's Lua state cannot be profiled this way.
- Save: a late-game save of the XL world, triggered with `radiant:client:save_game` from the client, returned after 3.5 s on vanilla (55,744 KB on disk in `saved_games/perf_bench_probe`, `server_state.bin` 56,582,393 bytes) and 4.6 s on ACE (70,156 KB). The autosave (every 5 real minutes when enabled, off in the harness) pauses the game around its save (`stonehearth/ui/root/js/root_view.js`), so saves of this length recur for players who keep it on. How much of the time the server is blocked was not measured.
