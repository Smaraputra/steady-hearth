# ACE notes

Notes for the ACE team: places where a small change improved performance or stability in our tests (clone pinned at `f55f2c146`, branch `unstable-work`) while building this program. This project does not modify, fork or send pull requests to the ACE repository. Fixes ship only as guarded patches inside `steady_hearth`. This file keeps the evidence in case they are useful upstream.

Every entry was checked against the source code. File paths are relative to the ACE root. Our benchmark is a stress test (4 towns of 28 hearthlings, 44 buildings), so an effect that grows with world size or session length is larger there than in a typical game, and several entries are small in normal play. Each entry says what its effect grows with where we know it. IDs follow the findings ledger series in `docs/atlas/findings.md`: E for ACE monkey patches, X for ACE services and components, F for ACE UI.

| E1 | `_request_placement_task` stores entries under `tasks[tag][key]`, but `_unrequest_placement_task` reads `tasks[key]` | `monkey_patches/ace_town.lua:1098-1145` | Placement task counts stay in the table for the session. Placement entries remain and placement AI continues to check them. Reviewed 2026-10-28: in the base game as well, `GhostFormComponent:_remove_from_town` unrequests only inside its `_limited_registration_tag` block (base `ghost_form_component.lua:139-148`, ACE `ace_ghost_form_component.lua:36-50`) while `_add_to_town` requests for every placeable item type, so in both games an entry outlives its ghosts unless the item has a placement limit. Each worker with a placement action cycles through the entries one at a time with a 5 s realtime failsafe (`place_item_type_on_structure_2.lua`, `build_item_type_on_structure.lua`): the search cost per worker is bounded, but each stale entry delays real placement requests by up to 5 s per pass. Measured by the census `placement_tasks` probe (`44a241e`): after two game days every placement entry in all 4 towns is stale (64 entries, 0 live ghosts), in ACE and in vanilla. |
| E2 | `AceEvolveComponent:activate` calls `_create_listeners()` twice, so the first season listener reference is overwritten and the listener remains active | `monkey_patches/ace_evolve_component.lua:52,65,90-97` | Every evolve entity with `evolve_data.seasons` (about 165 entity definitions) that evolves leaves an active `stonehearth.seasons` listener. The cost is small: on a season change a live entity recalculates its evolve timer twice (the second pass is a no-op that recreates the same timer), and a destroyed entity's retained listener finds no timer and only writes its own multiplier table. Memory grows with the number of seasonal evolve entities ever activated, with no per-tick cost. Low priority. |

Base-game behaviours that ACE already addresses, so they are not duplicated: the growing timer re-armed after maturity (ACE guards with `is_finished`), inventory tracker `mark_changed` batching, the water height replication flood, and buff modifier restore on load.

## Measured cost (XL benchmark, 2026-10-27)

| Variant | Complete runs | Real seconds per game day | Realized speed | Lua heap at end |
| :--- | :--- | :--- | :--- | :--- |
| Vanilla | 4 | 257.1 s mean (252.7 to 263.6, CoV 1.8%) | 336 | 269 MiB |
| ACE | 2 | 488.4 s mean (441.4 and 535.4) | 179 | 494 MiB (2026-10-27 scenario) |

Under the same 4-player late-game load, runs with ACE need about 1.9 times the real time per game day and 1.8 times the Lua heap. The time is concentrated in multi-second pauses rather than spread evenly: the median per-sample speed under ACE (307 to 314) is within 10% of vanilla (328 to 341), while the engine logged native job-list passes of up to 25 s. Details and the pause breakdown are in `docs/harness/bench.md`.
